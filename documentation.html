1. Project Overview & Executive Summary

1.1 Purpose, Mission & Cultural Heritage Scope

“អាហារ & ទេសចរណ៍ខ្មែរ” (Khmer Food & Tourism) is a high-performance, cross-platform mobile application engineered to catalog, promote, and preserve Cambodia's authentic culinary heritage and natural, cultural, and historical tourism attractions across all 25 provinces.

The application solves a critical gap in regional tourism: fragmented, unverified, and outdated information regarding traditional recipes, authentic provincial restaurants, eco-tourism resorts, and cultural monuments. By unifying 200 authentic Khmer recipes with cooking instructions and nutritional values, 220+ verified provincial restaurants and street-food stalls, and 300 curated tourist destinations into a lightning-fast offline-first native mobile application, the program acts as an essential digital companion for domestic travelers, international tourists, culinary researchers, and restaurant owners.

1.2 Verified Core Metrics (Current Release: v1.8.9 Build 61)

300 Tourist Destinations

Covers all 25 provinces (dest-1 to dest-300) with zero duplicate records, verified GPS coordinates, entry fees, and authentic landmark imagery.

200 Authentic Khmer Dishes

Categorized across soups, grilled meats, stir-fries, salads, desserts, noodles, rice, and specialties with full ingredient lists and step-by-step recipes.

220+ Verified Restaurants

Authentic provincial dining spots, Google Maps deep links, verified telephone dialers, photo galleries, and 10 VIP benefit integrations.

Hardware Biometrics

Native Android BiometricPrompt integration with AndroidKeyStore AES-256-GCM hardware vault for instant one-touch admin fingerprint entry.

Bakong KHQR Payments

National Bank of Cambodia (NBC) standard KHQR integration, direct ABA Mobile Bank deep-linking, and two-way slip verification.

Zero-Duplicate Engine

Integrated pre-save duplicate detector cross-verifying Khmer root names, English titles, and GPS coordinates within 100 meters.

1.3 Architecture Highlights & Key Design Principles

  • Offline-First Availability: All 300 destinations, 200 foods, and core restaurant metadata reside within pre-bundled JSON/TS seed assets and synced localStorage databases. The app operates smoothly without internet access.
  • Zero Ingestion Latency: App startup and search operations execute synchronously in under 16ms, maintaining a continuous 60-120 FPS mobile UI.
  • Strict Principle of Least Privilege: Non-paying and unapproved users cannot access restaurant modification endpoints. VIP memberships expire strictly by timestamp calculations, preventing unauthorized privilege retention.
  • Defense in Depth: Master credentials undergo 100,000-iteration PBKDF2 hashing with cryptographic salts; sensitive storage data is sanitized; brute-force attacks trigger automatic 15-minute lockout thresholds.

2.3 Hybrid Native Mobile Bridge (Capacitor 8.5.3)

The program utilizes Capacitor 8.5.3 as the native runtime shell. Rather than using legacy Cordova containers, Capacitor exposes direct Java/Kotlin reflection bindings into the Android OS, wrapping the compiled Vite web assets (dist/) inside android/app/src/main/assets/public/.

The native application entry point is MainActivity.java (inheriting from BridgeActivity), which automatically configures the hardware-accelerated Android WebView, injects Capacitor bridges, registers custom plugins, and handles Android lifecycle pauses and resumes.

2.4 Custom Native Android Java Plugins

  • NativeBiometricAuthPlugin.java: Integrates Android's BiometricPrompt and BiometricManager. It generates and holds an AES-256-GCM master key inside the hardware-backed AndroidKeyStore (StrongBox / TEE). When authenticating, it prompts the fingerprint dialog, encrypts/decrypts the admin credential token on success, and returns it to the webview without exposing raw passwords in user space.
  • NativeAbaLauncherPlugin.java: Manages external app intent resolutions and deep links. It queries packages such as com.paygo24.ibank and com.ababank.mobile, opens ABA Mobile directly to complete KHQR payment workflows, and falls back to universal web links if banking apps are absent.
  • NativeGoogleAuthPlugin.java: Connects to Google Play Services Auth (com.google.android.gms.auth.api.signin) allowing users to link genuine Google accounts directly on physical devices.

6. Data and Image Management Pipeline

6.1 Multi-Format Image Ingestion & Validation

Images are ingested through normalizeAndValidateImage() in TouristImageModal.tsx and validateImageUpload() in security.ts. The system supports four distinct formats:

  • HTTP / HTTPS URLs: Standard public web URLs (e.g. Wikimedia Commons). Validated via new URL(url).
  • Data URLs (data:image/...;base64,...): Generated by in-app camera capture or gallery file selection. The Base64 payload is validated to confirm presence of valid image data.
  • Raw Base64 Strings: Direct Base64 payloads (pasted without URI prefixes). The engine detects MIME signatures automatically (e.g., /9j/ for JPEG, iVBOR for PNG, UklGR for WebP) and prefixes them properly.
  • Local Bundled Assets: Relative local paths (e.g. /destinations/dest-58.jpg or /foods/food-1.jpg) served directly from Android assets or Vite public folders for offline rendering.

6.2 Client-Side Image Compression & Optimization Pipeline

To prevent mobile memory bloat and stay within browser localStorage limits, images selected via gallery or camera pass through client-side canvas compression: 

// Client-side image compression & WebP conversion
const compressImageFile = (file: File, maxWidth = 1200, maxHeight = 800, quality = 0.85): Promise<string> => {
  return new Promise((resolve, reject) => {
    const reader = new FileReader();
    reader.onload = (e) => {
      const img = new Image();
      img.onload = () => {
        let { width, height } = img;
        if (width > maxWidth || height > maxHeight) {
          const ratio = Math.min(maxWidth / width, maxHeight / height);
          width = Math.round(width * ratio);
          height = Math.round(height * ratio);
        }
        const canvas = document.createElement('canvas');
        canvas.width = width;
        canvas.height = height;
        const ctx = canvas.getContext('2d');
        ctx.fillStyle = '#FFFFFF';
        ctx.fillRect(0, 0, width, height);
        ctx.drawImage(img, 0, 0, width, height);
        
        try {
          const webp = canvas.toDataURL('image/webp', quality);
          if (webp.startsWith('data:image/webp')) {
            resolve(webp);
            return;
          }
        } catch {}
        resolve(canvas.toDataURL('image/jpeg', quality));
      };
      img.src = e.target.result as string;
    };
    reader.readAsDataURL(file);
  });
};

6.3 Real-Time Sync & Cache-Busting Architecture

In version 1.8.9, image updating in TouristDetailModal.tsx was overhauled to ensure persistent saving:

  1. When an image is saved in TouristImageModal, the callback calls updateDestination(updatedDest), updates selectedDestination, and sets setEditPhotoUrl(updatedDest.photoUrl) immediately.
  2. Images are bound with dynamic React key attributes (key={editPhotoUrl || selectedDestination.photoUrl}), forcing the DOM to remount and display the new photo without browser cache interference.
  3. updateDestination performs a direct synchronous write to localStorage.setItem('kft_destinations_real_v7', JSON.stringify(next)) to persist changes before any page reloads can occur.

7.2 Detailed Analysis: Issue #1 (Destination Photo Save Bug)

Root Cause Breakdown

In TouristDetailModal.tsx, when an administrator clicked "ប្តូររូបភាព" and saved a new image in TouristImageModal, the onSave callback omitted setEditPhotoUrl(updatedDest.photoUrl). Because of this, the parent form input retained the old photo URL. When the user subsequently clicked "រក្សាទុកព័ត៌មាន", the form submitted the old URL and overwrote the change. Furthermore, upon app reload, AppContext.tsx contained logic that reverted non-data: URLs to seed values. Both issues have been corrected in v1.8.9.

7.3 Detailed Analysis: Issue #2 (Duplicate Siem Reap Record)

Audit Resolution

A full database audit revealed that dest-20 (Angkor Night Market & Pub Street) and dest-123 (Siem Reap Pub Street & Night Market) were duplicate entries sharing coordinates 13.3547, 103.8548. To preserve existing user bookmarks and links referencing dest-123, the record was updated to represent Phnom Bakheng Hilltop Sunset Temple (13.4239, 103.8561), a major UNESCO Angkor monument that was previously missing from the dataset.

8. Security, Cryptography, and Backup Procedures

8.1 Password Cryptography (PBKDF2-HMAC-SHA256)

Passwords are hashed using NIST SP 800-132 recommendations: PBKDF2 with HMAC-SHA256, 100,000 iterations, and a 32-byte cryptographic salt generated via crypto.getRandomValues(). 

// Cryptographic password derivation (100,000 rounds)
export const hashPasswordPBKDF2 = async (password: string, saltHex?: string): Promise<string> => {
  const salt = saltHex || generateSaltHex(32);
  const enc = new TextEncoder();
  const passwordKey = await crypto.subtle.importKey('raw', enc.encode(password), { name: 'PBKDF2' }, false, ['deriveBits']);
  const saltBytes = new Uint8Array(salt.match(/.{1,2}/g)?.map(byte => parseInt(byte, 16)) || []);
  const derivedBits = await crypto.subtle.deriveBits(
    { name: 'PBKDF2', salt: saltBytes, iterations: 100000, hash: 'SHA-256' },
    passwordKey,
    256
  );
  return `${salt}:${Array.from(new Uint8Array(derivedBits)).map(b => b.toString(16).padStart(2, '0')).join('')}`;
};

8.2 Brute-Force Rate Limiting & Account Lockout

  • Maximum 5 consecutive failed login attempts allowed before lockout.
  • 15-minute lockout timer enforced via timestamp tracking in security.ts.
  • Hash comparisons utilize constant-time string equality to prevent timing attacks.

8.3 Security Audit Logging System

Authentication and administrative actions are recorded in kft_security_audit_log. The logger stores structured events while sanitizing sensitive data (passwords, tokens, and PII are never logged). The log retains the 100 most recent entries.

8.4 Backup Architecture & Disaster Recovery Manual

1. Automated Daily Backups

Scheduled batch jobs (Daily_Auto_Backup.bat) run nightly, archiving system databases, configuration states, and asset uploads to F:\Soft\System Program 2027 kimseng\Back up DATA every day\.

2. Version Control (Git)

Full codebase history is versioned in GitHub (main branch) with annotated release tags (v1.0.0 through v1.8.9). Every release builds a verified APK artifact.

3. Seed Database Backups

Data integrity is anchored by versioned seed files: seedDestinations.ts, seedData.ts, touristDestinationsList.json, and master Excel files (KhmerFoodTourism_All_300_Destinations.xlsx).

4. Disaster Recovery Procedure

In the event of client data corruption, clearing localStorage triggers automatic re-hydration from compiled seed files. Critical administrative keys can be re-provisioned via the emergency unlock protocol.

10. Future Roadmap & Technical Recommendations

10.1 Short-Term Enhancements (Priority 1)

  • Cloud Image CDN Offloading: Shift from storing compressed Base64 Data URLs in client storage to an external object storage bucket (e.g., Supabase Storage or Cloudinary) with automated CDN caching.
  • Push Notifications (Firebase Cloud Messaging): Implement native FCM messaging to notify users when their VIP payment is approved by the admin.

10.2 Medium-Term Architectural Upgrades (Priority 2)

  • Bi-directional Cloud Sync: Connect the local AppContext store with Supabase real-time subscriptions, allowing changes made by the admin to propagate instantly to user devices without requiring app updates.
  • Multi-Language Voice Search: Add speech-to-text recognition in Khmer and English for hands-free food and destination lookups while traveling.

10.3 Long-Term Vision (Priority 3)

  • Google Play Store Production Track: Submit the pre-configured Signed Android App Bundle (AAB) to Google Play Store production review using existing keystore assets.
  • Interactive Offline Vector Maps: Embed MapLibre / OpenStreetMap vector tiles for offline topographic navigation in remote eco-tourism destinations.
