# សុវត្ថិភាព VIP — Phase B2 (ជំហានទី 1)

## បញ្ហា
VIP ត្រូវបានផ្តល់ដោយ **កម្មវិធីខ្លួនឯង**។ អ្នកណាមាន key សាធារណៈ (មានក្នុង APK ទាំងអស់) សរសេរ `membershipTier: "premium_vip"` ក្នុងជួរ `kft_user_*` ក៏បាន VIP ឥតគិតថ្លៃ — សូម្បីតែ **បង្កើតជួរថ្មី** (trigger ចាស់ការពារតែ UPDATE/DELETE)។ ការផ្ទៀងផ្ទាត់វិក្កយបត្រក៏ធ្វើក្នុងកម្មវិធីដែរ ដូច្នេះអាចគេចបាន។

## អ្វីដែលបានបង្កើត
| ផ្នែក | ការងារ |
|---|---|
| **`vip-purchase` Edge Function** | Server អានវិក្កយបត្រ (Gemini) ហើយពិនិត្យ៖ អ្នកទទួលផ្លូវការ · ចំនួនទឹកប្រាក់ត្រូវនឹងតម្លៃ **នៅ Server** · កាលបរិច្ឆេទ ≤14 ថ្ងៃ · **ត្រូវតែអាន Trx ID បានពីវិក្កយបត្រ** (លែងបង្កើត Trx ID ក្លែងពី fingerprint) · មិនធ្លាប់ប្រើ។ ជោគជ័យទាំងអស់ → Server សរសេរ VIP ក្នុង `kft_user_<id>` ដោយ service role។ បើមិនច្បាស់ → `pending` ឱ្យ Admin ពិនិត្យ |
| **`kft_payment_receipts`** | បញ្ជីវិក្កយបត្រឯកជន ជាមួយ **UNIQUE image hash** និង **UNIQUE Trx ID (verified)** → វិក្កយបត្រតែមួយប្រើបានតែម្តងគត់ ទោះមានសំណើស្របគ្នា |
| **`kft_vip_grant_guard`** (SQL) | trigger លើ `kft_user_*` (INSERT និង UPDATE) ។ «ការផ្តល់» = VIP ក្លាយជាសកម្ម ឬកាលបរិច្ឆេទផុតកំណត់ប្តូរទៅក្រោយ ឬ `paidAdditionalStoreSlots` កើនឡើង។ អ្នកទុកចិត្ត៖ service role, SQL Editor, token Admin។ **រៀបចំតាមមុខងារ**៖ `off` / `shadow` (កត់ត្រា ប៉ុន្តែអនុញ្ញាត) / `on` (ត្រឡប់ទៅតម្លៃដើម) |
| **កម្មវិធី** | ការទិញ VIP តាម KHQR សួរ Server មុន ហើយប្រើកាលបរិច្ឆេទរបស់ Server។ ប្រើការផ្ទៀងផ្ទាត់ចាស់ក្នុងឧបករណ៍ **តែពេល Function មិនដំណើរការ**។ ការផ្តល់ VIP ដោយ Admin ផ្ញើ token Admin ជាមួយ |

## សុចរិតភាព៖ អ្វីដែលនៅមិនទាន់ដោះស្រាយ
- **វិក្កយបត្រ screenshot អាចក្លែងបាន**។ AI អានអក្សរលើរូប មិនអាចដឹងថារូបត្រូវបានកែ ឬមិនមែនពី ABA ពិត។ ដំណោះស្រាយពិត = ពិនិត្យប្រតិបត្តិការជាមួយ **Bakong API** (MD5 របស់ KHQR) ឬ webhook របស់ធនាគារ។ ឥឡូវនេះយើងកំណត់បានតែ៖ (1) វិក្កយបត្រមួយប្រើបានតែម្តង, (2) ទាមទារ Trx ID + អ្នកទទួល + ចំនួន + កាលបរិច្ឆេទ, (3) Admin ឃើញបញ្ជី `kft_payment_receipts`។ ក្រោយនេះអាចបន្ថែម Bakong ពេលមាន token។
- **លំហូរ VIP ក្នុងកម្មវិធីដែលមិនមានការទូទាត់** (ឧ. រង្វាន់ check-in 30 ម្ហូប ផ្តល់ VIP ឥតគិតថ្លៃ, ការ «បន្តដោយស្វ័យប្រវត្តិ» ដោយគ្មានការទូទាត់ពិត) នឹងត្រូវបានឃើញក្នុង shadow ហើយ **នឹងត្រូវបាន revert ពេលបើក `on`** លុះត្រាតែផ្ទេរទៅ Server។ ត្រូវសម្រេចចិត្តជាមួយគ្នាមុនបើក `on`។
- **ការទិញកន្លែងបន្ថែម (additional store slot)** និង **VIP ក្នុងហាង** ប្រើលំហូរវិក្កយបត្រដាច់ដោយឡែក ដែល Server មិនទាន់ផ្ទៀងផ្ទាត់ (guard កត់ត្រាតែ `paidAdditionalStoreSlots`)។ ជំហានបន្ទាប់។
- `GooglePlayBilling` នៅក្នុងកូដជាស្លាកតែប៉ុណ្ណោះ គ្មាន Billing library ពិត → មិនមានការទិញក្នុង Play Store ពិតទេ។
- Admin ឥឡូវអនុម័តវិក្កយបត្រ `pending` តាមផ្លូវចាស់ (សរសេរ VIP ដោយ token Admin)។ ការភ្ជាប់ទៅ `kft_payment_receipts` (ដើម្បីឃើញស្ថានភាព) ជាជំហានបន្ទាប់។

## ✅ របៀបអនុម័តលំនាំដើម = **ដោយដៃ ដោយ Admin ផ្ទៀងផ្ទាត់ជាមួយ statement ធនាគារ** (ការសម្រេចចិត្តរបស់ម្ចាស់កម្មវិធី)
លោកអ្នកមិនចង់ប្រើ Bakong API / ABA API ទេ ដូច្នេះ **`vip-purchase` មិនបើក VIP ដោយស្វ័យប្រវត្តិទៀតទេ** (លុះត្រាតែកំណត់ secret `VIP_AUTO_APPROVE=true` ដែលមិនណែនាំ)។
- គ្រប់វិក្កយបត្រត្រូវបានរក្សាទុកជា `pending` ជាមួយ **ការពិនិត្យជាមុនដោយ AI** (អ្នកទទួល ✓ ចំនួន ✓ កាលបរិច្ឆេទ ✓ លេខប្រតិបត្តិការ ✓) ដែលបង្ហាញឱ្យ Admin ឃើញក្នុងប្រតិបត្តិការ `pending_verification`។
- **Admin ពិនិត្យ statement ក្នុងគណនី ABA៖ ស្វែងរក Trx ID + ចំនួន + ពេលវេលា** (មិនមែនរូបភាពទេ) ហើយចុចអនុម័តក្នុងផ្ទាំង Admin ដូចធម្មតា។ ដោយសារអនុម័តដោយមនុស្សពី statement ពិត **វិក្កយបត្រក្លែងមិនអាចទទួលបាន VIP ទេ**។
- ការអនុម័តដោយ Admin សរសេរ VIP ដោយ token Admin ដែល trigger `kft_vip_grant_guard` ទទួលស្គាល់ (ដូច្នេះនៅដំណើរការ ទោះបើក `on`)។
- Trx ID តែមួយ មិនអាចត្រូវបានឆ្លើយបានពីរដង (pending ឬ verified) ហើយរូបភាពតែមួយមិនអាចប្រើពីរដង។
- **បង្កើនល្បឿនពេលក្រោយ (ជម្រើស)**៖ ទាញ statement ពី ABA ជាឯកសារ (CSV/Excel) ហើយបង្កើតប៊ូតុង «ផ្គូផ្គងស្វ័យប្រវត្តិ» ដែលរកឃើញ Trx ID ដែលស្របគ្នា ហើយបង្ហាញបញ្ជី «ត្រូវគ្នា» ឱ្យ Admin ចុចអនុម័តតែម្តងច្រើនជួរ។ នៅតែ Admin ជាអ្នកសម្រេច មិនត្រូវការ API ពីធនាគារ។
